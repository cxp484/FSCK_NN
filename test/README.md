# Test the NN model using Fortran and ONNX Runtime

The comparison is compiled Fortran. Python is used only to plot the output CSV.

## Build and run from FSCK_NN

```bash
export ONNXRUNTIME_ROOT=/absolute/path/to/extracted/onnxruntime-sdk
bash test/build.sh
mkdir -p test/results/new_onnx_comparison
test/build/compare_fsck training/runs/my_smoke/best.onnx \
  test/grid.nml \
  /path/to/FSKTableV4 \
  test/results/new_onnx_comparison/comparison.csv

# Python only reads the completed CSV and plots it.
python3 -m pip install -r test/requirements.txt
python3 test/plot_results.py test/results/new_onnx_comparison/comparison.csv
```

The executable takes four positional arguments: ONNX model, grid namelist,
database root, and output CSV. Create the output directory first. Existing CSV
and plot files at the selected paths are overwritten.

Requirements for compilation: `gfortran`, a C compiler, and the ONNX Runtime
C/C++ SDK (not bundled). This interface was tested with ONNX Runtime 1.20.1
on macOS ARM64. Download the matching SDK from <https://github.com/microsoft/onnxruntime/releases> and set:

```bash
export ONNXRUNTIME_ROOT=/absolute/path/to/extracted/onnxruntime-sdk
bash test/build.sh
```

The SDK must have `include/onnxruntime_c_api.h` and `lib/libonnxruntime`.
The Python `onnxruntime` package is not required and does not replace this SDK.
`FC` and `CC` select the compilers; the current flags target gfortran and
Clang/GCC on macOS/Linux. The build embeds the SDK library path as an rpath.
Keep the SDK in place, or rebuild after moving it.

## Fortran ONNX interface

`nn_model.f90` exposes:

```fortran
use nn_model, only: read_model, predict, close_model
! state(7) and kappa(32) are real(real64).
call read_model('training/runs/my_smoke/best.onnx')
call predict(state, kappa)
call close_model()
```

`read_model` opens one persistent ONNX Runtime session. `predict` calls the
C ABI in `onnx_bridge.c` through `ISO_C_BINDING`; ONNX Runtime executes the
network. There is no manual Fortran MLP or weight-text export. Inputs are
converted to float32, passed as `[1,7]`, and float32 outputs are returned as
Fortran double precision. Preprocessing and conversion from log10 kappa are
already inside the ONNX graph and are not repeated in Fortran.

Use ONNX models generated by `training/train_fsck.py`. They must expose one
float32 input named `physical_inputs`, in the order
`P_atm, xCO2, xH2O, xCO, fv, Tgas_K, Tref_K`, and one float32 output named
`kappa` with 32 values in native database units. The batch dimension may be
dynamic or one. Tensor names, dimensions, and types are checked on loading.
The test uses the original 32 database quadrature points; the model must use
that same quadrature convention. Inference does not load `.pt` files.

Trained models are not bundled. First run the smoke-training command in
`training/README.md`, or substitute your own ONNX model path. Training exports
`best.onnx` and `last.onnx` automatically.

## Grid and a-function

Edit `test/grid.nml`, a Fortran namelist:

```fortran
&grid
  pressures = 1.0, 1.5
  co2 = 0.015, 0.035
  h2o = 0.015, 0.035
  co = 0.005, 0.025
  soot = 5e-8, 5e-7
  tgas = 950, 1450
  tref = 1100, 1600
/
```

Fortran constructs the Cartesian product: this example gives 128 states.
Provide contiguous lists of up to 100 values per axis, with a maximum of one
million total states. Pressure is in atm, gases are mole fractions, soot is
volume fraction, and temperatures are in K. Every axis is required. Intermediate
database values are supported; out-of-range values and mixtures with gas mole
fractions summing above unity are rejected.

`compare_fsck.f90` calls the original `loadIntoMem` and `get_ka` in the preserved
`fortran/fskTableV4.f90`. It calls ONNX twice per state, at `(Tgas,Tref)` and
`(Tgas,Tgas)`, then passes both NN curves to the same `afun` routine used for
direct access. Database interpolation and its original tolerances are unchanged.

The original loader reads pressure brackets and composition/temperature prefixes
up to the required limits, so memory and I/O can grow much faster than the
requested state count. All bounding files must be present. Start with the small
supplied grid.

## Outputs

- `comparison.csv`: inputs, quadrature nodes/weights, database and NN kappa/a,
  and a monotonicity flag for each state/node pair.
- `comparison.csv.meta`: model, grid, and database paths used by Fortran.
- `k_parity.png` / `.pdf`: 1:1 kappa plots, linear and logarithmic.
- `a_parity.png` / `.pdf`: 1:1 stretching-function plots, linear and logarithmic.
- `summary.json`: errors, finite-value counts, monotonicity, negative a counts,
  and discrete normalization from the CSV.

The dashed line is exact agreement. Log plots include only positive finite
pairs; linear plots retain negative values. No sorting or normalization is
applied. Nonmonotone NN kappa curves violate `afun` assumptions, so their
calculated a-values are colored orange and labeled **diagnostic only**.

Comparison results are generated locally and are not bundled. A smoke-trained
model verifies the workflow; it is not a production surrogate.
